# Design Audit: Forms Screen

*Audited against the Apple Human Interface Guidelines (1987 Desktop Interface)*
*Date: February 7, 2026*

---

## Audit Summary: Form Components

### Critical Issues (Fix Immediately)

1. **[Checkboxes Use "v" Text Instead of Standard Check Marks — HIG 2.7, 1.4]**: The checkbox controls render a lowercase letter "v" as the checked indicator rather than a proper checkmark glyph (✓) or a filled/toggled checkbox control. Users must interpret an ambiguous letter as a boolean state. HIG 2.7 requires standard check box controls that are "accompanied by text labels" with a universally recognizable checked/unchecked visual. HIG 1.4 (Consistency) demands that standard controls follow platform conventions so users don't need to learn new idioms.
   → **Fix**: Replace the "v" character with a proper checkmark icon (✓ or ✔) inside a visible checkbox frame. Use a filled box with checkmark for checked, and an empty box for unchecked — the universally recognized checkbox pattern. This eliminates ambiguity and brings the control into line with platform conventions.

2. **[Unchecked Checkboxes Have No Empty Box Indicator — HIG 2.7, 3.1, 8.1]**: When a checkbox is unchecked ("Fullscreen," "Show FPS"), the control displays only the label text with no visible empty box or other affordance indicating it is a togglable control. Users have no visual cue that these labels are interactive checkboxes rather than static text. HIG 2.7 states check boxes must have visible on/off states. HIG 3.1 requires that "color coding is redundant with shape/position/pattern" — here there is no shape or pattern differentiator at all, only the absence of a "v."
   → **Fix**: Always display a checkbox frame (empty square) next to the label, regardless of checked state. Checked = frame with checkmark inside; unchecked = empty frame. This makes the interactive affordance visible at all times and removes reliance on the presence/absence of a single character.

3. **[Dropdown Indistinguishable from Checkbox — HIG 1.4, 1.10]**: The "English v" dropdown at the bottom of the right column uses the same "v" indicator as the checkboxes above it. There is no disclosure arrow, caret, or border treatment to distinguish it as a dropdown/popup menu. Users cannot tell whether "English v" is a checked checkbox or a selectable dropdown. HIG 1.10 states that "different things look different," and HIG 1.4 requires consistent use of standard controls where the same visual treatment always means the same interaction type.
   → **Fix**: Use a distinct disclosure indicator for dropdowns — a downward-pointing triangle/chevron (▾) instead of "v." Add a visible container border or background treatment that differs from checkboxes. The dropdown should be visually identifiable as a popup menu at a glance.

4. **[Sliders Lack Visible Thumb/Handle — HIG 1.2, 2.7]**: The slider controls (Volume, Brightness, Difficulty) display as flat colored bars with a percentage label but no visible draggable thumb or handle. HIG 1.2 (Direct Manipulation) requires that users can "directly grab, move, and manipulate objects on screen" with a sense of "grabbing" or "moving." Without a visible thumb, users cannot identify the grab target or perceive the control as directly manipulable. The slider looks more like a progress bar than an interactive control.
   → **Fix**: Add a visible slider thumb — a circle, knob, or rectangular handle — at the current value position on the track. The thumb should be visually distinct from the filled and unfilled portions of the track and should respond to hover/press states. This is the primary affordance that communicates "drag me."

5. **[Progress Bars Visually Identical to Sliders — HIG 1.10, 1.4]**: The "Progress Bars" section (Audio Level: 75%, Level Progress: 75/100) renders controls that are visually indistinguishable from the sliders above. Both use the same horizontal bar with a colored fill and text label. HIG 1.10 explicitly warns against "different things looking the same." Progress bars are read-only indicators; sliders are interactive controls. Conflating them teaches users the wrong interaction model.
   → **Fix**: Visually differentiate progress bars from sliders. Options include: (a) use a different bar height (thinner for progress), (b) use a different fill color or pattern (e.g., striped/hatched fill), (c) remove the slider thumb from progress bars (this already happens but the slider also lacks a thumb, so there's nothing to remove), or (d) add a different border treatment. The two component types must be immediately distinguishable.

### Major Issues (Fix Soon)

6. **[Inconsistent Section Header Colors — HIG 1.4]**: The "Sliders" and "Checkboxes" headers use a teal/dark cyan background, while "Progress Bars" uses a vivid red/magenta background. There is no semantic reason for the color difference — both are section headers at the same hierarchy level within the same panel. HIG 1.4 requires that the same type of element receives the same visual treatment. The red header draws disproportionate attention to a less important section.
   → **Fix**: Use a single, consistent background color for all section headers within the form panel. If color variation is needed for semantic purposes (e.g., red for warnings), document and apply the convention systematically. Otherwise, all peer-level headers should be identical.

7. **[Low Contrast Text Throughout — HIG 3.2, 8.1]**: The screen uses light teal/cyan text on dark navy backgrounds across most elements. While the general contrast is adequate for large text, smaller labels like "Brightness: 50%," "Difficulty: 30%," and the status bar text ("Volume: 75% | Resolution: 1920x1080 | Quality: Medium") appear at reduced sizes where the teal-on-navy combination falls below comfortable legibility. HIG 3.2 requires "text and thin lines have sufficient contrast to be easily visible." HIG 8.1 requires high contrast availability.
   → **Fix**: Increase the lightness of body text or decrease the lightness of backgrounds to achieve at least a 4.5:1 contrast ratio for all text sizes. Consider using white or near-white text for labels and reserving teal for decorative elements or headers.

8. **[Disabled State Insufficiently Communicated — HIG 1.9, 3.1]**: The "Disabled" dropdown in the right column uses a gray color to indicate its inactive state, but the treatment is subtle — it still appears as a clickable control with a "v" indicator. HIG 1.9 requires that "unavailable items are dimmed, not removed," but the dimming must be clear enough that users recognize the control is non-interactive. The current gray treatment is too close in value to the active controls' dark teal.
   → **Fix**: Apply a more pronounced disabled treatment: significantly reduce opacity (40–50%), remove or gray out the "v" indicator, and optionally add a subtle strikethrough or desaturated pattern. The disabled state must be immediately recognizable as non-interactive without requiring comparison to active controls.

9. **[Paste Button Uses Destructive-Action Red — HIG 1.4, 3.2]**: The "Paste" button at the bottom of the screen uses a bright red/crimson background, a color universally associated with destructive or dangerous actions (delete, remove, stop). Pasting is a constructive, non-destructive action. This color choice misleads users about the severity and nature of the action. HIG 1.4 requires consistent conventions, and red-for-danger is a deeply ingrained platform convention.
   → **Fix**: Change the Paste button to a neutral or constructive color — the same teal used elsewhere, or a distinct but non-alarming accent color. Reserve red exclusively for destructive actions (delete, clear, reset) so the color carries consistent semantic meaning.

10. **[Selected/Focused State Too Subtle — HIG 1.7, 5.1]**: The Volume slider appears to have a focused/selected state indicated by a thin white dashed border. This focus indicator is extremely subtle against the dark background — it is barely distinguishable from the unfocused sliders. HIG 1.7 requires "immediate feedback confirms every action" and HIG 5.1 requires "visual feedback shows what's selected." A nearly invisible focus ring defeats both principles.
    → **Fix**: Make the focus indicator more prominent: use a solid white or bright-colored border (2–3px), a glow/shadow effect, or a contrasting background highlight. The selected element must be instantly identifiable at a glance.

11. **[Monospace Font Reduces Label Readability — HIG 7.1, 1.10]**: The entire screen uses a monospace/pixel-style typeface for all text — headers, labels, values, and status text. Monospace fonts have lower readability for labels and body text because uniform character widths make word shapes harder to recognize at a glance. While thematically appropriate for a retro game UI, it impacts quick scanning of form labels like "Brightness: 50%" and "Level Progress: 75/100."
    → **Fix**: If the monospace font is a deliberate game-UI design choice, keep labels short (1–2 words) and increase font size or letter spacing to compensate. Consider using a more readable proportional font for form labels while keeping monospace for decorative elements, or ensure the monospace font has clearly differentiated letterforms.

### Minor Issues (Consider Fixing)

12. **[Status Bar Lacks Visual Grouping — HIG 1.10, 1.7]**: The status bar at the bottom of the form panel ("Volume: 75% | Resolution: 1920x1080 | Quality: Medium") packs three unrelated settings into a single line separated by pipe characters. The information has no visual grouping — it reads as a single run-on string rather than three distinct status indicators. HIG 1.10 requires clear visual hierarchy, and the bar's flat formatting treats all three values as equally important and related.
    → **Fix**: Separate the status items with more visual structure — use distinct background segments, icons, or increased spacing between items. Alternatively, if these values update dynamically in response to form changes, highlight the changed value momentarily to connect cause and effect per HIG 1.7.

13. **[Clipboard Section Competes with Form Controls for Attention — HIG 1.10]**: The "Clipboard Demo" section at the bottom of the screen has nearly the same visual weight as the form components panel above it. The instructional text ("Copy saves current settings, Paste retrieves saved text") is the same size and color as other labels. The "(clipboard empty)" indicator is rendered in a large, high-contrast style that draws the eye more than the actual form controls. HIG 1.10 warns against "flat visual hierarchy — everything same prominence."
    → **Fix**: Reduce the visual prominence of the clipboard demo section — use a smaller font for the instructional text, a more subdued treatment for the clipboard status area, and ensure the primary form components panel is the clear focal point of the screen.

14. **[No Visual Grouping Between Related Checkboxes — HIG 2.7]**: The checkboxes list (Music, SFX, Fullscreen, V-Sync, Show FPS) contains items that logically belong to different groups — audio settings (Music, SFX), display settings (Fullscreen, V-Sync, Show FPS) — but they are all rendered in a single undifferentiated vertical list with identical spacing. HIG 2.7 requires that related controls be "visually distinct" in their grouping and that radio button/checkbox groups be separated from one another.
    → **Fix**: Add visual separators (a subtle horizontal line or increased spacing) between logically distinct groups of checkboxes. Alternatively, add sub-headers ("Audio," "Display") to organize the checkboxes into meaningful clusters.

15. **[Mixed Value Formats — HIG 1.4, 7.1]**: The screen uses inconsistent formats for displaying values: "75%" (percentage), "50%" (percentage), "30%" (percentage), "75/100" (fraction), "1920x1080" (dimensions). The sliders use percentage notation while "Level Progress" uses fractional notation for what appears to be a percentage value (75/100 = 75%). HIG 1.4 (Consistency) requires uniform treatment of similar data, and HIG 7.1 requires clear, simple language.
    → **Fix**: Standardize the value format. If percentage notation is the convention, display "Level Progress: 75%" instead of "75/100." If the fraction format is intentional (showing current/max), apply it consistently to other controls as well (e.g., "Audio Level: 75/100"). Choose one convention and apply it uniformly.

16. **[Column Divider Is Too Subtle — HIG 1.10]**: The vertical separation between the Sliders/Progress Bars column (left) and the Checkboxes column (right) is either a very thin line or simply whitespace. The two columns are not clearly delineated as distinct sections, making the layout feel like a loosely scattered collection of controls rather than two organized panels. HIG 1.10 requires that visual design supports understanding and structure.
    → **Fix**: Add a clearer visual divider between columns — a visible vertical line, a subtle background color difference, or distinct container borders for each column. This reinforces the two-column structure and helps users parse the layout quickly.

17. **[No Cancel/Reset Mechanism Visible — HIG 1.8, 2.5]**: The form presents interactive controls (sliders, checkboxes, dropdown) but shows no way to reset values to defaults or cancel changes. HIG 1.8 (Forgiveness) requires that users can "recover from mistakes easily" with undo available for content-changing operations. HIG 2.5 requires a Cancel button in dialogs with form controls. The clipboard demo offers Copy/Paste but no Undo or Reset.
    → **Fix**: Add a visible "Reset to Defaults" or "Undo" control, either globally for the entire form or per-section. This assures users they can experiment with settings without fear of losing their original configuration.

18. **[Title Bar Uses Same Color as Active Controls — HIG 1.10, 3.2]**: The "Form Components" title header uses the same teal/cyan color as the interactive checkbox and slider controls below it. This makes the title blend into the control surface rather than standing out as a page heading. HIG 1.10 requires that "different things look different" — the page title and interactive controls are fundamentally different element types that should have distinct visual treatments.
    → **Fix**: Differentiate the title from interactive elements — use a different background color, larger font size, bolder weight, or a unique border treatment. The title should immediately read as a non-interactive heading, not as another form control.

### Strengths

- **Clear Two-Column Layout**: The form organizes sliders and progress bars in the left column and checkboxes in the right column, creating a logical spatial grouping that separates control types. Users can scan one column for adjustment controls and the other for toggle options.
- **Inline Value Display on Sliders**: Each slider displays its current value directly in the label (e.g., "Volume: 75%"), providing immediate WYSIWYG feedback without requiring users to look elsewhere. This follows HIG 1.5 and 1.7 by showing current state visibly and directly.
- **Consistent Dark Theme**: The overall dark navy color scheme is cohesive across all elements and gives the screen a unified visual identity appropriate for a game UI settings panel.
- **Status Bar Provides Context**: The status bar at the bottom summarizes key settings in a single visible location, giving users a quick reference for the current configuration without navigating away from the form.
- **Disabled State Attempted**: The "Disabled" dropdown demonstrates an inactive control state, showing awareness that controls need to communicate availability. While the execution needs improvement, the intent to showcase disabled state is correct.

### Overall Score: 3/10

The Forms screen demonstrates a reasonable organizational structure — the two-column layout, inline value labels, and status bar show thoughtful intent — but it is undermined by critical failures in control design and visual communication. The most damaging issues are the non-standard checkbox representation (a "v" character with no visible empty-box affordance for unchecked states), the indistinguishable dropdown and checkbox controls, and the nearly identical appearance of sliders and progress bars. These three issues together mean that a user encountering this screen for the first time cannot reliably identify what type of control they are looking at or what interaction it supports. For a form components showcase — which should serve as a reference implementation for developers — these are fundamental failures. The typography, color, and contrast choices further reduce usability, and the absence of a slider thumb removes the primary affordance for the screen's most prominent interactive elements. Structural improvements to control differentiation, focus indicators, and visual hierarchy would significantly elevate the design.
