# Design Audit: Modal Dialogs Screen

*Audited against the Apple Human Interface Guidelines (1987 Desktop Interface)*
*Date: February 7, 2026*

---

## Audit Summary: Modal Dialogs

### Critical Issues (Fix Immediately)

1. **[Inconsistent Button Styling Across Same Screen — HIG 1.4, 1.10]**: The buttons on this single screen use at least five completely different visual treatments: "Simple Modal" has a thin white outline with no fill, "Composable Modal" has a solid purple/magenta fill, "Info Dialog" has a dark teal fill, "Confirmation" has a crimson/red fill, "Notice" has a muted mauve fill, and "Open Settings" / "Background Button" use yet another dark teal variant. These are all peer-level trigger buttons performing the same class of action (opening a modal), yet they look radically different from one another. HIG 1.4 requires that "visual styles [are] consistent throughout" and that the "same action produces same result throughout the application."
   → **Fix**: Establish a single, consistent button style for all modal-trigger buttons. If color is used to hint at the modal's semantic meaning (info vs. confirmation vs. notice), use a uniform button shape, size, border treatment, and typography, with only a subtle color accent varying. The current approach makes every button look like it belongs to a different application.

2. **[Color as Sole Differentiator Between Modal Types — HIG 3.1, 8.1]**: The "Info Dialog," "Confirmation," and "Notice" buttons rely entirely on fill color (teal, crimson, mauve) to communicate their different semantic meanings. On a monochrome display, or to a colorblind user, all three would appear as identically shaped rectangles with similar-value fills. HIG 3.1 states that "color coding is redundant with shape/position/pattern" and that a design must "work in black and white first."
   → **Fix**: Add secondary differentiators: pair each button with a severity icon (info circle, warning triangle, bell/notice), use different border treatments (solid, dashed, double), or vary the button shape. Each modal type must be distinguishable without relying on color alone.

3. **[No Default Button Indicated — HIG 2.5, 2.7]**: None of the buttons on the screen is visually marked as a default action. HIG 2.5 explicitly requires that the "default button is doubly outlined" and activated by Return/Enter. In a modal dialog showcase, demonstrating the default button convention is essential — its absence means developers using this toolkit have no reference for how primary actions should be styled.
   → **Fix**: Add a visible default button indicator — either a double-outline or a heavier/bolder treatment — to whichever button represents the primary action. At minimum, demonstrate this convention in the "Basic Modals" section.

4. **[No Cancel Mechanism Visible — HIG 1.8, 2.5]**: The screen shows buttons that launch modals but demonstrates no way to dismiss or cancel them. HIG 2.5 states "Cancel button always available" and HIG 1.8 (Forgiveness) requires that users be able to "cancel in all dialogs." A modal showcase that omits the cancel pattern teaches developers to build inescapable dialogs.
   → **Fix**: Either show a preview of the modal's cancel/dismiss affordance in the showcase, or add explicit text noting that each modal includes a cancel button. The showcase should demonstrate both the trigger and the escape path.

5. **[Flat Visual Hierarchy — HIG 1.10]**: All sections (Basic Modals, Helper Functions, Modal Stacking, Input Blocking Test, Results) have nearly identical visual weight. The section headers are tiny, low-contrast uppercase text, while the buttons and status text compete for attention at similar prominence levels. HIG 1.10 warns against "flat visual hierarchy — everything same prominence" and requires "clear visual hierarchy — most important elements stand out."
   → **Fix**: Create a clear hierarchy: make section headers larger and higher-contrast so they serve as navigation landmarks, make the primary demo buttons visually dominant, and reduce the prominence of secondary/status elements like "BG Clicks: 0" and the Results row. The eye should follow a clear path from title → section → action.

### Major Issues (Fix Soon)

6. **[Section Headers Too Small and Low Contrast — HIG 3.2, 8.1]**: The section headers ("BASIC MODALS," "HELPER FUNCTIONS," "MODAL STACKING," etc.) use very small, all-caps text in a low-contrast color against the dark background. They are barely readable and fail to serve their purpose as section labels. HIG 3.2 requires that "text and thin lines have sufficient contrast to be easily visible" and HIG 8.1 requires "high contrast available."
   → **Fix**: Increase the font size of section headers by at least 50%, use a higher-contrast color (e.g., light gray or white instead of the current muted tone), and consider adding a bottom border or spacing below the header to strengthen the visual separation between sections.

7. **[No Severity Icons for Dialog Types — HIG 2.6]**: The "Info Dialog," "Confirmation," and "Notice" buttons represent three standard alert severity levels, but none includes the corresponding icon. HIG 2.6 requires an "icon [that] indicates severity: Note 📝, Caution ⚠️, Stop 🛑." Without icons, users have no visual shorthand for the dialog's purpose or urgency.
   → **Fix**: Add severity icons to each helper function button and/or demonstrate them in the resulting modals: an info circle for Info Dialog, a caution/question mark for Confirmation, and a bell or note icon for Notice. These icons should also appear inside the modal dialogs themselves when opened.

8. **[Technical/Programmer Language in Status Display — HIG 7.1]**: The Results section shows "Confirm: Pending | FYI: Pending | Confirms: 0 Cancels: 0" — this uses pipe-delimited formatting, the abbreviation "FYI," and developer-centric terminology. HIG 7.1 requires "user vocabulary, not programmer vocabulary" and forbids "jargon or technical terms." Similarly, "BG Clicks: 0" uses an abbreviation ("BG") that is meaningless to end users.
   → **Fix**: Replace pipe-delimited text with a proper table or separated display. Spell out "FYI" as "Notice" to match the button label, rename "BG Clicks" to "Background Clicks" or "Blocked Click Attempts," and use natural language formatting instead of debug-style output.

9. **[Inconsistent Button Sizes — HIG 1.4]**: The buttons vary significantly in width and height with no discernible system. "Simple Modal" is a narrow outlined box, "Composable Modal" is wider with a larger font, "Info Dialog" is medium-width, "Confirmation" is compact, and "Notice" is wider with larger text. Within the same row, buttons that serve parallel purposes should share the same dimensions. HIG 1.4 requires consistent visual treatment for the same type of element.
   → **Fix**: Standardize button heights within each row. Either use a consistent fixed width for all buttons or let content determine width with consistent horizontal padding. At minimum, all buttons within the same section should share the same height and font size.

10. **[Inconsistent Typography Across Button Labels — HIG 1.4, 1.10]**: Button labels appear in at least three different text sizes: "Simple Modal" uses a smaller font, "Composable Modal" and "Notice" use a noticeably larger font, and "Confirmation" uses a medium font. Within the same functional group (Helper Functions), the three buttons have three different text sizes. This inconsistency undermines the sense of a unified design system.
    → **Fix**: Establish a single font size for all standard buttons. If size variation is used semantically (e.g., primary vs. secondary), document the convention and apply it consistently. All buttons in the same row should use the same font size.

11. **[Buttons Lack Clear Interactive Affordance — HIG 1.2, 1.7]**: Several buttons blend into the dark background and don't clearly read as clickable controls. The "Simple Modal" button's thin outline is subtle, and "BG Clicks: 0" looks like it could be either a button or a static counter. HIG 1.2 requires that interactive elements provide a sense of direct control, and HIG 1.7 requires that feedback confirms every action. Without clear affordance, users cannot confidently identify what is clickable.
    → **Fix**: Ensure all buttons have consistent visual affordance — a fill color, border weight, or shadow that distinguishes them from static text and containers. Non-interactive elements like "BG Clicks: 0" should be styled distinctly from buttons (no border, different background treatment) so users don't confuse display elements with controls.

### Minor Issues (Consider Fixing)

12. **[Button Labels Are Nouns/Descriptions, Not Action Verbs — HIG 2.7]**: Most button labels describe what will appear ("Simple Modal," "Composable Modal," "Info Dialog," "Notice") rather than an action the user is taking. HIG 2.7 states that button "labels describe the action that will occur." The exception is "Open Settings (with nested confirm)," which correctly uses an action verb. A modal showcase should model best practices for button labeling.
    → **Fix**: Consider using action-oriented labels like "Show Simple Modal," "Open Info Dialog," or "Request Confirmation" to demonstrate proper button labeling conventions. Keep the descriptive text as subtitle or tooltip if needed, but lead with the verb.

13. **[Excessive Nesting Creates Visual Clutter — HIG 1.10]**: The screen has three levels of visual nesting: the outermost dark background, a slightly lighter container panel, and then individual section containers within it. Each section has its own horizontal bar/header plus a content area, creating a repetitive "box in box in box" pattern. HIG 1.10 warns against "visual clutter" and "decoration that distracts from function."
    → **Fix**: Reduce nesting to two levels. Either remove the outer container and let sections float on the page background with generous spacing, or remove the individual section containers and use the outer container with simple dividers between sections.

14. **[No Hover, Focus, or Pressed States Demonstrated — HIG 1.7, 5.1]**: The showcase displays buttons only in their resting state. For a modal dialog toolkit, demonstrating interactive states (hover, focus ring, pressed/active) is important so developers know how their buttons will behave. HIG 1.7 requires "immediate feedback confirms every action" and HIG 5.1 requires "visual feedback shows what's selected."
    → **Fix**: Add a section demonstrating button interactive states, or include annotations noting what visual feedback occurs on hover/press. At minimum, ensure the underlying component library provides distinct hover and pressed treatments.

15. **[Results Section Mixes Data Display Styles — HIG 1.4, 1.10]**: The Results section uses a monospace, pipe-delimited format ("Confirm: Pending | FYI: Pending | Confirms: 0 Cancels: 0") that looks like terminal output or a debug log. This clashes with the rest of the screen's visual style and fails to present information in a user-friendly way. The mixing of label:value pairs with counters in a single unstructured line makes it hard to scan.
    → **Fix**: Display results in a structured grid or card layout — each value in its own labeled cell with consistent alignment. Use the same visual container style as the rest of the screen. Separate "current state" indicators (Pending/Confirmed) from "cumulative counters" (Confirms: 0, Cancels: 0) into distinct visual groups.

16. **[Monospace Typography Reduces Readability — HIG 7.1, 1.10]**: The entire screen uses a monospace/pixel-style typeface for all text — title, headers, button labels, and status text alike. Monospace fonts have lower readability for labels and UI text because uniform character widths make word shapes harder to recognize at a glance. While thematically consistent with a game UI, it makes the information density harder to parse, especially in the Results section.
    → **Fix**: If the monospace font is a deliberate game-UI design choice, compensate by keeping labels short, increasing font size, and adding generous spacing between elements. Consider using a proportional font for body/status text while keeping monospace for headers or decorative elements.

17. **[No Visual Distinction Between Modal Categories — HIG 1.10, 3.1]**: The five sections (Basic Modals, Helper Functions, Modal Stacking, Input Blocking Test, Results) all use identical container styling — same background color, same border treatment, same spacing. While container consistency is generally good, these sections represent fundamentally different concepts (trigger types, interaction patterns, testing tools, output displays). Some visual differentiation would help users orient themselves.
    → **Fix**: Consider subtle section-level differentiation: a slightly lighter background for interactive demo sections vs. the Results/status section, a different left-border accent color per section, or icons next to section headers to provide quick visual anchors.

18. **[Title Bar Styling Doesn't Communicate Hierarchy — HIG 1.10, 2.1]**: The "Modal Dialogs" title at the top is rendered inside a teal/cyan container bar that looks more like a navigation tab or status bar than a page title. It shares the same visual language as the section header bars below it (teal horizontal bands), making it unclear whether "Modal Dialogs" is a page title, a section header, or a clickable element. HIG 1.10 requires that "different things look different."
    → **Fix**: Give the title distinctly different treatment from section headers — use a larger font, different background color or no background, more vertical space above and below, or a different typographic weight. The title should unmistakably read as the page-level heading.

### Strengths

- **Logical Section Organization**: The screen is divided into meaningful categories — Basic Modals, Helper Functions, Modal Stacking, Input Blocking Test, and Results — that progressively demonstrate modal concepts from simple to complex. This supports learning and discoverability.
- **Comprehensive Modal Coverage**: The showcase covers a good range of modal patterns — simple modals, composable modals, helper functions (info, confirm, notice), modal stacking, and input blocking — providing a thorough reference for developers.
- **Cohesive Dark Theme**: The overall dark color scheme is internally consistent and provides a unified visual identity appropriate for a game UI toolkit.
- **Input Blocking Test Section**: Including a dedicated section to demonstrate that modals properly block background interaction is thoughtful and addresses a common source of bugs. The "BG Clicks" counter provides concrete evidence of blocking behavior.
- **Status Feedback Mechanism**: The Results section provides real-time feedback on modal interactions (confirm/cancel counts, pending states), supporting HIG 1.7's requirement for feedback on user actions — even if the formatting needs improvement.

### Overall Score: 3/10

The Modal Dialogs screen has a sound organizational structure and covers an impressive range of modal patterns, but the visual execution undermines its effectiveness as both a showcase and a design reference. The most damaging issue is the wildly inconsistent button styling — buttons that serve the same purpose (launching a modal) use five different visual treatments, teaching developers that arbitrary variation is acceptable. Color is the sole differentiator between dialog severity levels (info, confirmation, notice), failing colorblind users and violating the HIG's core principle that designs must work without color. The visual hierarchy is flat, with section headers barely readable and all sections competing at the same visual weight. Technical jargon in the status display, missing severity icons, absent cancel affordances, and no default button convention round out a pattern of overlooking the HIG's fundamental guidelines. For a toolkit showcase — which serves as a reference implementation that developers will copy — these issues are particularly consequential because they normalize poor patterns across every application built with the toolkit.
