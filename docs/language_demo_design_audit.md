# Design Audit: Language Demo Screen

*Audited against the Apple Human Interface Guidelines (1987 Desktop Interface)*
*Date: February 7, 2026*

---

## Audit Summary: Language Demo

### Critical Issues (Fix Immediately)

1. **[Keyboard Shortcuts as Primary Interaction — HIG 1.3, 8.3]**: The footer reads "Press 1/2/3 to switch languages," presenting keyboard shortcuts as the primary (and only documented) method for switching languages. The language tabs in the top-right corner are present but tiny and visually de-emphasized. HIG 1.3 (See-and-Point) explicitly states that "keyboard shortcuts are *alternatives*, never the only way" and warns against "features only accessible via keyboard shortcuts." Users should be able to discover and select a language by clicking, not by memorizing a key mapping.
   → **Fix**: Make the language tabs in the top-right corner larger, more visually prominent, and clearly clickable. The tabs should be the primary interaction method, with "Press 1/2/3" noted as a secondary shortcut beneath or beside the tabs. Remove the footer instruction or reframe it as supplementary: "Tip: Press 1, 2, or 3 for quick switching."

2. **[Color as Sole Indicator of Active Language Tab — HIG 3.1, 8.1]**: The active language tab (EN / English) is distinguished from the inactive tabs (KO / Korean, JA / Japanese) solely by its green background color. There is no difference in shape, border weight, size, position, icon, or pattern between active and inactive tabs. A colorblind user or a monochrome display would render all three tabs identically. HIG 3.1 requires that "color coding is redundant with shape/position/pattern" and that the design "works in black and white first."
   → **Fix**: Add a secondary visual indicator for the active tab — a thicker bottom border, an underline, a slightly raised/inset appearance, a checkmark icon, or a size/weight change. The active tab must be identifiable without color.

3. **[Color as Sole Indicator of Selected Button — HIG 3.1, 5.1, 8.1]**: The "Hello!" button is distinguished from the other buttons (Start, Settings, About, Exit, Continue) solely by its gold/mustard fill color. All other buttons share a dark blue fill with a lighter border. No difference in shape, border weight, icon, or pattern communicates the selected state. HIG 5.1 requires "visual feedback shows what's selected (highlighting/inverse)" and HIG 3.1 requires color coding to be redundant with other visual cues.
   → **Fix**: Add a non-color indicator for the selected button — a left-edge accent bar, a filled vs. outline treatment, a bolder border, a checkmark or arrow icon, or a slight size/inset change. The selected item must be distinguishable from unselected items without color.

4. **[Language Tabs Are Illegibly Small — HIG 3.2, 8.1, 1.10]**: The language selector tabs in the top-right corner are extremely small relative to the rest of the interface. The text within them ("EN English [1]", "KO Korean [2]", "JA Japanese [3]") is cramped and difficult to read at normal viewing distance. HIG 3.2 requires that "text and thin lines have sufficient contrast to be easily visible" and that "small objects use high-contrast colors." HIG 8.1 requires support for larger text for vision accessibility. These tabs are critical interactive elements — the entire language-switching feature depends on them — yet they receive the smallest visual treatment on the screen.
   → **Fix**: Increase the tab size significantly — at least 2–3x their current area. Use a larger font size for the language names. Position them more prominently, either as a row of full-width tabs below the title bar or as a clearly visible button group within the right panel. Critical interactive elements must be appropriately sized.

5. **[Flat Visual Hierarchy — HIG 1.10]**: The screen's two main content panels (left button list, right language preview) have identical visual treatment — same dark rounded container, same border style, same background shade. The title bar, the two panels, and the footer all compete for attention at nearly equal visual weight. HIG 1.10 requires "clear visual hierarchy — most important elements stand out" and warns against "flat visual hierarchy — everything same prominence." It is unclear what the primary content area is — the button list or the language preview.
   → **Fix**: Establish a clear visual hierarchy. If the left panel is the primary interaction area, give it more visual weight (slightly lighter background, larger size proportion, or a subtle border emphasis). If the right panel is the primary output, make it more prominent. Differentiate the title bar from the content containers, and reduce the footer's visual weight so it reads as secondary information.

### Major Issues (Fix Soon)

6. **[Inconsistent Text Alignment in Right Panel — HIG 1.4, 1.10]**: The three language entries in the right panel (EN, KO, JA) are positioned at different horizontal offsets. "EN: Hello! – Start" sits at one indent level, "KO: 안녕하세요! – 시작" is indented further to the right, and "JA: こんにちは? – 開始" is indented at yet another position. This staggered layout creates a messy, unstructured appearance. HIG 1.4 (Consistency) requires visual styles to be consistent throughout, and HIG 1.10 warns against "visually confusing displays."
   → **Fix**: Left-align all three language entries at the same horizontal position. Use a consistent layout — either a uniform left margin for all rows, or a two-column format where the language code (EN:, KO:, JA:) forms a left-aligned column and the translated text forms a second aligned column.

7. **[No Visual Connection Between Selection and Output — HIG 1.7, 1.5]**: The left panel shows a list of translatable strings with "Hello!" selected (gold), but the right panel shows translations for two different strings ("Hello!" and "Start") for each language. There is no visual linkage — no arrow, highlight, color coding, or spatial proximity — connecting the selected item on the left to its corresponding translation on the right. HIG 1.7 (Feedback) requires that feedback be "brief, direct" and clearly connected to the action. HIG 1.5 (WYSIWYG) requires the screen to clearly represent state.
   → **Fix**: Either (a) show only the translation for the currently selected string (e.g., "Hello!" → "안녕하세요!" → "こんにちは?"), (b) highlight the corresponding translations in the right panel with a matching color or style, or (c) add a visual connector (line, arrow, or shared background) between the selected item and its translations.

8. **[Footer Text Has Insufficient Contrast — HIG 3.2, 8.1]**: The footer text ("Active: ENGLISH | Font: Gaegu-Bold" and "Press 1/2/3 to switch languages") uses a medium-light color on the dark background. While it is more legible than some elements, it still has a relatively low contrast ratio, particularly the smaller "Press 1/2/3" line. HIG 3.2 requires that "text and thin lines have sufficient contrast to be easily visible."
   → **Fix**: Increase the footer text brightness or use a higher-contrast treatment. The "Active: ENGLISH" line contains important state information and should be clearly readable. Consider using a slightly lighter background strip or brighter text color for the footer area.

9. **[Monospace/Handwritten Font Reduces Readability — HIG 7.1, 1.10]**: The entire screen uses the "Gaegu-Bold" font, a handwritten-style typeface. While thematically charming for a game UI, handwritten fonts have lower readability than standard proportional fonts, especially for UI labels and small text. The irregular letter shapes make word recognition slower, particularly for the Korean and Japanese text which may not render well in this typeface. HIG 7.1 requires messages to be "concise and simple" and HIG 1.10 warns against decoration that "distracts from function."
   → **Fix**: If the handwritten font is a deliberate design choice, ensure it is only used for display/title elements. Use a cleaner, more legible font for interactive labels (button text, tab text, footer text). At minimum, verify that the Korean and Japanese glyphs render clearly and legibly in this typeface, as CJK characters in non-native fonts often suffer from poor glyph quality.

10. **[Unclear Purpose of Right Panel Content — HIG 1.7, 7.1]**: The right panel displays "All Languages" as a heading followed by three lines showing the translations of "Hello!" and "Start" in English, Korean, and Japanese. It is not immediately clear what this panel's purpose is — is it a preview, a reference, a translation comparison, or debug output? The heading "All Languages" is vague. HIG 7.1 requires text to be "concise and simple" using "user vocabulary, not programmer vocabulary."
   → **Fix**: Provide a clearer heading that explains the panel's purpose, such as "Translation Preview" or "Selected Text in All Languages." Add a brief description or contextual label so users understand what they are looking at and why.

11. **[Two-Panel Layout Has Unbalanced Content Density — HIG 1.10]**: The left panel contains six buttons stacked vertically with generous spacing, filling its container well. The right panel contains only four lines of text (a heading and three translations) floating in a large empty space. This creates a strong visual imbalance — the left panel feels dense and functional while the right panel feels sparse and incomplete. HIG 1.10 requires designs to be "visually clear" with graphics that "support understanding, not just decoration."
    → **Fix**: Either (a) reduce the right panel's size to match its content, (b) add more content to the right panel (e.g., show translations for the selected string plus adjacent strings, or display the active language's full string list), or (c) use a different layout that doesn't create two equal-sized containers with unequal content.

### Minor Issues (Consider Fixing)

12. **[Language Code Abbreviations Assume User Knowledge — HIG 1.3, 7.1]**: The right panel uses ISO language codes (EN, KO, JA) as prefixes for each translation line. While "EN" for English is widely understood, "KO" for Korean and "JA" for Japanese are less intuitive for general users. HIG 1.3 warns against "cryptic abbreviations or codes" and HIG 7.1 requires "user vocabulary, not programmer vocabulary."
    → **Fix**: Use full language names ("English:", "Korean:", "Japanese:") or, if space is constrained, add the full name after the code ("EN (English):", "KO (Korean):", "JA (Japanese):"). Alternatively, use flag icons alongside the codes for quick visual recognition.

13. **[Inconsistent Button Label Punctuation — HIG 1.4]**: The first button label "Hello!" includes an exclamation mark, while all other button labels (Start, Settings, About, Exit, Continue) do not use any punctuation. This inconsistency is visually jarring in a vertically stacked list where uniformity is expected. HIG 1.4 requires "terminology consistent — same words for same concepts" and consistent visual styles throughout.
    → **Fix**: Standardize punctuation across button labels. Either remove the exclamation mark from "Hello!" (making it "Hello") or accept it as a translatable greeting string and visually distinguish it from the action buttons below it (e.g., by separating it with a divider or giving it a different styling treatment as a display/greeting element rather than a navigation button).

14. **[Mixed Semantic Roles in Button List — HIG 1.4, 2.7]**: The left panel mixes a greeting display ("Hello!") with navigation actions (Start, Settings, About, Exit) and a continuation action (Continue). "Hello!" is not an action a user would "click to perform" — it's a string preview or greeting label. Placing it as the first button in a navigation list conflates display content with interactive controls. HIG 2.7 requires button "labels describe the action that will occur."
    → **Fix**: Separate the greeting/display string ("Hello!") from the navigation buttons. Either move it above the button list as a preview label, or visually distinguish it with a different component type (e.g., a text display rather than a button). The button list should contain only actionable items.

15. **[No Hover/Focus/Active State Indication — HIG 1.7, 5.1]**: The button list shows only two states — selected (gold fill for "Hello!") and unselected (dark blue fill for all others). There is no visible hover state, focus ring for keyboard navigation, or pressed/active state. HIG 1.7 requires "immediate feedback confirms every action" and HIG 5.1 requires "visual feedback shows what's selected."
    → **Fix**: Demonstrate or implement hover (lightened fill or border highlight), focus (visible focus ring for keyboard users), and pressed/active (darkened fill or inset appearance) states for the buttons. These are essential for communicating interactivity.

16. **[Tab Keyboard Shortcut Numbers Are Bracketed and Small — HIG 1.3, 3.2]**: The keyboard shortcuts "[1]", "[2]", "[3]" in the language tabs are rendered in brackets at the same small size as the tab text. The brackets add visual clutter and the numbers are too small to be useful as a quick reference. HIG 3.2 requires small objects to use high-contrast colors, and HIG 1.3 requires keyboard shortcuts to be clearly visible alternatives.
    → **Fix**: If keyboard shortcuts are displayed in the tabs, render them more clearly — use a slightly larger or bolder font for the number, or place it in a small key-cap style badge. Alternatively, display the shortcuts only in the footer instruction and remove them from the cramped tabs to reduce clutter.

17. **[Excessive Nesting of Visual Containers — HIG 1.10]**: The screen has three levels of visual nesting: the outer dark page background, a slightly lighter outer frame/container, and then the two inner panel containers. This "box in a box in a box" pattern adds visual complexity without conveying meaningful structural information. HIG 1.10 warns against "visual clutter" and decoration that "distracts from function."
    → **Fix**: Reduce to two nesting levels. Either remove the outer container (letting the panels sit directly on the page background) or remove the inner panel containers (using the outer container as the content boundary with internal dividers instead of sub-boxes).

18. **[Title Bar Does Not Clearly Separate from Content — HIG 1.10, 2.1]**: The "Language Demo" title bar uses a slightly brighter blue background than the content panels, but the distinction is subtle. The title bar and the content area blend together visually, especially at the left and right edges where they share the same container boundary. HIG 2.1 requires that title bars be visually distinct and HIG 1.10 requires different things to look different.
    → **Fix**: Increase the visual separation between the title bar and the content area. Use a more distinct background color, add a bottom border/divider line, or increase the vertical spacing between the title bar and the content panels.

### Strengths

- **Multilingual Support Demonstrated Clearly**: The screen effectively showcases the toolkit's ability to handle English, Korean, and Japanese text, which is a valuable capability to demonstrate.
- **Consistent Dark Theme**: The overall dark navy color scheme is cohesive and provides a unified visual identity appropriate for a game UI toolkit.
- **Logical Two-Panel Layout Concept**: The split between a selectable string list (left) and a translation preview (right) is a reasonable layout pattern for a localization demo.
- **Active Language State Communicated in Footer**: The footer explicitly states "Active: ENGLISH" and the current font name, providing useful status information.
- **Button List Is Well-Spaced**: The vertical spacing between buttons in the left panel is consistent and generous, making each button easy to identify and target.

### Overall Score: 3/10

The Language Demo screen demonstrates a useful feature (multilingual text support) but suffers from fundamental accessibility and usability failures. The most critical issue is the over-reliance on color as the sole differentiator for both the active language tab and the selected button — a direct violation of the HIG's core accessibility principle that designs must work without color. The language tabs are far too small to serve as primary interactive elements, pushing users toward the keyboard-shortcut-only "Press 1/2/3" method, which violates the See-and-Point principle. The handwritten font, while charming, impairs readability across three writing systems. The right panel's content is poorly organized with inconsistent alignment and unclear purpose. For a toolkit showcase — which should model best practices — these issues are particularly problematic because they demonstrate patterns that developers may replicate in their own applications.
