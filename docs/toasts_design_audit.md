# Design Audit: Toast Notifications Screen

*Audited against the Apple Human Interface Guidelines (1987 Desktop Interface)*
*Date: February 8, 2026*

---

## Audit Summary: Toast Notifications

### Critical Issues (Fix Immediately)

1. **[Color as Sole Differentiator Between Toast Types — HIG 3.1, 8.1]**: The Simple Toasts row uses color alone to communicate severity: teal for Info, dark green for Success, orange for Warning, and red for Error. There is no variation in shape, icon, pattern, or border treatment to distinguish these types. A colorblind user or someone on a monochrome display would see four nearly identical rectangles. HIG 3.1 explicitly states that "color coding is redundant with shape/position/pattern" and the design must "work in black and white first."
   → **Fix**: Add a distinct icon to each toast type button and to the resulting toast notification — an "i" circle for Info, a checkmark for Success, a triangle/exclamation for Warning, and a stop/X icon for Error. HIG 2.6 specifically prescribes severity icons (Note, Caution, Stop) for alert-like elements. Each type should also be distinguishable by shape or border treatment in addition to color.

2. **[No Visible Toast Preview — WYSIWYG Violation — HIG 1.5]**: The screen shows trigger buttons for toast notifications but never displays what the actual toasts look like. Users must click a button and wait for a transient popup to understand the output. This violates the WYSIWYG principle: "what's on screen is what exists" and "no abstract commands that 'promise' future results." A showcase for toast notifications should show the toast component itself, not just the buttons that produce them.
   → **Fix**: Add a static preview area showing what each toast type looks like when rendered — its background color, text layout, icon placement, and dismiss behavior. Alternatively, display persistent example toasts on screen alongside their trigger buttons so users can see the full component without needing to interact.

3. **[Inconsistent Button Sizing in Simple Toasts Row — HIG 1.4]**: The four toast type buttons in the Simple Toasts row are noticeably different sizes. "Error Toast" appears wider and taller than "Info Toast" and "Success Toast," and "Warning Toast" sits somewhere in between. These buttons represent parallel, equivalent options (four toast types) and should be identically sized. HIG 1.4 requires that "same action produces same result throughout" and visual styles must be consistent.
   → **Fix**: Standardize all four buttons in the Simple Toasts row to the same width and height. Use consistent internal padding so buttons with longer labels don't grow disproportionately — either use a fixed width for all four or ensure padding produces visually equal containers.

4. **[Flat Visual Hierarchy Across All Sections — HIG 1.10]**: All three content sections (Simple Toasts, Duration & Spam, Interactive Toasts) use identical dark container boxes with the same background color, border weight, and border radius. The title bar also uses a nearly identical container treatment. HIG 1.10 warns against "flat visual hierarchy — everything same prominence" and requires that "most important elements stand out." The three sections have fundamentally different purposes but are visually indistinguishable.
   → **Fix**: Differentiate the sections through varied container treatments — slightly different background lightness values, varying border styles, or distinct section icons. The title should be clearly a heading (no container, or a wider/differently-colored container). The most important section (Simple Toasts, the core demonstration) should be visually prominent relative to Duration and Interactive sections.

5. **[Focus Ring on Only One Button — HIG 1.4, 5.1]**: The "Info Toast" button has a visible white focus/selection ring around it while no other button on the screen does. If this indicates keyboard focus, it suggests navigability — but the inconsistency implies either a default selection or a broken focus state. HIG 5.1 requires "visual feedback shows what's selected" applied consistently, and HIG 1.4 requires consistent treatment across equivalent elements.
   → **Fix**: If the focus ring indicates the currently focused element, ensure it moves consistently as users navigate with keyboard/gamepad. If "Info Toast" is a default selection, clarify this with additional visual treatment (e.g., a "selected" label or a filled indicator). The focus ring style should be documented as part of the toast showcase so developers understand the keyboard navigation model.

### Major Issues (Fix Soon)

6. **[Excessive Color Palette — HIG 3.1]**: The screen uses at least eight distinct fill colors across its buttons: teal (Info Toast, Quick, Long), dark green (Success Toast), orange (Warning Toast), dark red (Error Toast), coral/salmon (Spam, Custom Color), peach/light salmon (Custom Color fill), purple (With Undo Action), and the section container dark navy. HIG 3.1 recommends a "limited palette (4–7 colors max for coding)" and warns against a "rainbow of colors overwhelming the interface."
   → **Fix**: Consolidate the color palette. Toast type buttons should use the semantic toast colors. Utility buttons (Quick, Long, Spam) should use a single neutral or secondary color since their purpose is controlling duration, not toast type. The Custom Color button should be visually separated as a special case with explanatory text.

7. **["Spam x5 (!)" Label Uses Programmer Jargon — HIG 7.1]**: The button labeled "Spam x5 (!)" uses technical/developer shorthand. The "x5" notation, the word "Spam," and the parenthetical exclamation mark are all programmer conventions that a non-technical user would not understand. HIG 7.1 requires "user vocabulary, not programmer vocabulary" and warns against "jargon or technical terms."
   → **Fix**: Rename to something descriptive like "Show 5 Toasts" or "Burst (5 at once)." If the exclamation mark indicates a warning about spammy behavior, express that in plain language: "Rapid Fire (5 toasts)" or add a subtitle explaining the behavior.

8. **[Missing Severity Icons for Alert-Type Content — HIG 2.6]**: Toast notifications are functionally alert boxes — they communicate information, success, warnings, and errors. HIG 2.6 explicitly requires that alert-type content include severity icons: Note (info), Caution (warning), and Stop (error). The toast trigger buttons have no icons, and based on the static screenshot, there is no indication the resulting toasts include icons either.
   → **Fix**: Add standard severity icons to both the trigger buttons and the rendered toast notifications. Info gets an "i" or note icon, Success gets a checkmark, Warning gets a caution triangle, and Error gets a stop sign or X icon. These icons provide essential redundancy with color for accessibility.

9. **[Section Headers Use ALL-CAPS — HIG 7.1, 1.10]**: The section labels "SIMPLE TOASTS," "DURATION & SPAM," and "INTERACTIVE TOASTS" are rendered in all-uppercase. All-caps text is significantly harder to read than title case or sentence case because word shapes become uniform rectangles, removing the ascender/descender cues that aid recognition. HIG 7.1 calls for "concise and simple" text, and HIG 1.10 requires visually clear displays.
   → **Fix**: Use title case ("Simple Toasts," "Duration & Spam," "Interactive Toasts") for section headers. This improves readability while still visually distinguishing headers from button labels through font weight or size rather than case transformation.

10. **[Monospace Typography Reduces Readability — HIG 7.1, 1.10]**: The entire screen uses a monospace/pixel-style typeface for all text — title, section headers, button labels, and the "Undos: 0" counter. Monospace fonts have lower readability for labels because character widths are unnaturally uniform, making word shapes harder to recognize at a glance. While thematically appropriate for a retro game aesthetic, it particularly hurts longer labels like "Quick (displays 1s)" and "With Undo Action."
    → **Fix**: If the monospace font is a deliberate game-UI design choice, keep button labels short (1–2 words max) and increase font size or letter spacing to compensate. Consider using a proportional font for section headers and descriptive text while keeping monospace for button labels, or ensure the chosen monospace font has well-differentiated letterforms.

11. **["Custom Color" Button Has Inconsistent Styling — HIG 1.4]**: The "Custom Color" button in the Duration & Spam row uses a distinctly different visual treatment from every other button on screen — it has a red/dark border, a light salmon/peach fill, and dark text, while all other buttons use saturated dark fills with light text. This makes it look like it belongs to a different UI system entirely. HIG 1.4 requires that the same type of element receives consistent visual treatment.
    → **Fix**: If this button demonstrates custom color theming, visually separate it from the Duration row (perhaps in its own "Custom Styling" section) and add explanatory text. If it's a peer of Quick/Long/Spam, it should use a similar base styling with only its unique color as the variation, not an entirely different fill/text/border treatment.

### Minor Issues (Consider Fixing)

12. **["Undos: 0" Counter Lacks Clear Association — HIG 1.7, 1.10]**: The "Undos: 0" text in the Interactive Toasts section is placed adjacent to the "With Undo Action" button but has no visual container, label, or connection line tying it to the button's behavior. It's unclear whether this counts total undos performed, undos available, or something else. HIG 1.7 requires that feedback be "brief, direct" and clearly connected to the action that produced it.
    → **Fix**: Visually associate the counter with the button — place it inside a labeled container ("Undo count: 0"), position it directly below the button with an arrow or connector, or integrate it into the button label itself ("With Undo Action (0 undos)"). Add a brief explanation of what the counter tracks.

13. **[Inconsistent Horizontal Spacing Between Buttons — HIG 1.4]**: The gaps between buttons vary across and within rows. In the Simple Toasts row, the gap between "Info Toast" and "Success Toast" appears different from the gap between "Warning Toast" and "Error Toast." In the Duration row, the gap before "Custom Color" is noticeably larger than the gaps between the first three buttons. HIG 1.4 requires consistent spacing as a basic layout principle.
    → **Fix**: Standardize horizontal gaps between buttons within each row using a single spacing token (e.g., 12px or 16px). If "Custom Color" needs visual separation from the duration buttons, use a section divider or place it in its own sub-group rather than relying on an inconsistent gap.

14. **[Title Row Visually Identical to Content Sections — HIG 1.10]**: The "Toast Notifications" title is rendered inside a container box that uses the same styling (dark background, rounded corners, border) as the three content sections below it. The only differentiator is that the title text is centered — but the container treatment makes the title read as just another content card rather than a page heading. HIG 1.10 requires clear visual hierarchy where the most important elements stand out.
    → **Fix**: Remove the container box from the title or give it a distinctly different treatment — wider, no background, larger font size, or a different alignment. The title should unmistakably read as a heading, not as a content row.

15. **[Interactive Toasts Section Underutilized — HIG 1.7, 1.8]**: The Interactive Toasts section contains only a single button ("With Undo Action") and a counter. For a section labeled "Interactive," this is sparse. It doesn't demonstrate other common interactive toast patterns — dismiss buttons, action links, progress toasts, or multi-action toasts. HIG 1.8 (Forgiveness) emphasizes undo availability, but only one pattern is shown.
    → **Fix**: Expand the Interactive Toasts section to showcase additional patterns: a toast with a dismiss/close button, a toast with a custom action link (e.g., "View Details"), a toast with a progress bar, or a toast requiring confirmation. This makes the showcase more complete and useful as a reference implementation.

16. **[No Visual Indication of Toast Duration Behavior — HIG 1.5, 1.7]**: The Duration section has "Quick (displays 1s)" and "Long (displays 10s)" buttons, but there is no visual representation of how duration affects the toast. Users must click each button and mentally time the result. HIG 1.5 (WYSIWYG) requires that the screen show reality, and HIG 1.7 (Feedback) requires clear communication of timing behavior.
    → **Fix**: Add a visual indicator next to each duration button — a small timeline graphic, a progress bar mockup, or at minimum a more prominent duration label. Consider showing a side-by-side comparison of a short vs. long toast with a visible timer or progress indicator to communicate the temporal difference.

17. **[Outer Container Creates Triple Nesting — HIG 1.10]**: The screen has three levels of visual nesting: the dark page background, a slightly lighter outer container wrapping all content, and then the individual section containers within it. This "box in a box in a box" effect adds visual complexity without communicating meaningful structure. HIG 1.10 warns against "visual clutter."
    → **Fix**: Reduce nesting to two levels — either remove the outer container (let section cards float directly on the page background) or remove the individual section containers (let content sit inside the outer container with horizontal dividers instead of boxes).

18. **[No Demonstrated Keyboard/Gamepad Navigation — HIG 5.3, 8.3]**: Despite the focus ring on "Info Toast," the showcase does not demonstrate or document how keyboard or gamepad users navigate between toast trigger buttons or interact with active toasts. For a game UI toolkit — where gamepad is a primary input — this is a significant omission. HIG 5.3 requires keyboard navigation support, and HIG 8.3 requires alternatives for motor-impaired users.
    → **Fix**: Add a visual indicator or documentation showing the navigation order between buttons (tab order or D-pad flow). Show how an active toast can be dismissed or its action triggered via keyboard/gamepad input. Consider adding a "Navigation Demo" label or visual arrows showing the focus traversal path.

### Strengths

- **Logical Section Organization**: The showcase is divided into three meaningful categories — Simple Toasts (types), Duration & Spam (timing behavior), and Interactive Toasts (action-based) — which provides a clear conceptual framework for understanding toast capabilities.
- **Cohesive Dark Theme**: The overall dark navy color scheme is consistent and creates a unified visual identity appropriate for a game UI toolkit, with the darker content areas providing good contrast against the page background.
- **Duration Labels Are Informative**: The parenthetical duration hints — "(displays 1s)" and "(displays 10s)" — communicate expected behavior directly on the button, following HIG 1.7's principle that feedback should be immediate and understandable.
- **Undo Pattern Demonstrated**: Including an interactive toast with an undo action demonstrates HIG 1.8 (Forgiveness) — showing that toasts can support reversible actions, not just passive notifications.
- **Section Labels Are Present**: Each section has a visible label identifying its purpose, which aids discoverability and follows HIG 1.3's see-and-point principle.

### Overall Score: 3/10

The Toast Notifications showcase has a sensible organizational structure but suffers from fundamental design issues that undermine both accessibility and usability. The most critical problem is the complete reliance on color to differentiate toast severity types (Info, Success, Warning, Error) without any icon, shape, or pattern redundancy — a direct violation of the HIG's core accessibility principles. The showcase also violates WYSIWYG by showing only trigger buttons without any preview of the actual toast component being demonstrated. The inconsistent button sizing, excessive color palette, programmer-oriented labels ("Spam x5 (!)"), and triple-nested container layout further degrade the experience. For a toolkit showcase — which should serve as a reference implementation of best practices — these issues are particularly concerning because they signal to developers that color-only severity coding and invisible component previews are acceptable patterns.
