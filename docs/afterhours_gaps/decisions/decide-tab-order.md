# decide: tab order by tree or visual position, with scopes (Tier 2; hanabi, floatinghotel)

**Problem.** Tab order is the order in which `HandleTabbing` visits entities, and that is collection (creation) order. `process_tabbing` streams through it: forward sets focus to ROOT so the next `try_to_grab` takes it, and backward uses `last_processed`. Because order follows creation, pooled or virtualized rows tab in the order they were allocated. floatinghotel's file tree needed 7 Tab presses to reach the first row (step17). Order also cannot be bounded. Tab in one hanabi pane walks out into the sidebar and the other pane (#336). `FocusClusterRoot` only moves the ring and never affects navigation.

**Options**
1. **Tree order only (about 30 lines).** `HandleTabbing` walks the UI tree pre-order from the roots, the way `ResolveHitTarget` already does, instead of iterating the collection. For flex layouts, tree order is visual order, which fixes floatinghotel's virtual-list case. Behaviour change: any app whose creation order differs from tree order gets a different Tab sequence, and e2e scripts that press Tab N times may need updating.
2. **Tree order plus `with_focus_scope()` (about 90 lines). Recommended.** Each frame, build the ordered list of focusable ids instead of streaming. Tab and Shift+Tab move to the next or previous id within the nearest `FocusScope` ancestor of the focused element, and wrap at its edges. An element outside every scope uses the whole list. This covers hanabi's split panes and dialogs that should trap Tab. It replaces the `last_processed` streaming, and `WidgetMod` reverse tab keeps working.
3. **Option 2 plus focus groups** (one Tab stop per group, arrows inside it, focus remembered by item identity across pooled entities). This is floatinghotel's step-18 ask. It overlaps `HasTray` and virtual lists. Do it as a follow-up once scopes exist.

**Recommendation:** option 2 as one PR. Option 1 alone changes every app's Tab order without fixing #336, so changing order and adding scopes together means callers absorb the behaviour change only once. Rough size: about 90 lines in `context.h` and `systems.h` plus a config setter, a test covering tree order, scope wrap and reverse, and an example. The CHANGELOG would list the Tab-order change under Breaking.
