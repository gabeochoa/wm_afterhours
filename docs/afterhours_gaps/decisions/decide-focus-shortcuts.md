# decide: focus-scoped shortcut dispatch (Tier 2; floatinghotel, cartographer)

**Problem.** Each frame `UIContext` holds one mapped action in `last_action`, and the first `pressed()` call consumes it. Whoever polls first wins, which in practice means system registration order. It is not decided by where focus is. floatinghotel (U5) polls raw key codes for Find, Quick Open and the review commands in three systems, then checks by hand whether a text input, a menu, a source tab or a comment box has focus. It wants a chord offered first to the focused control, then to each enclosing scope, then to the app, and consumed once. The stale-`last_action` half of its report is already fixed on main: `BeginUIContextManager` clears it every frame. cartographer's doc has no shortcut-routing evidence I could find. The only cartographer entry nearby is the e2e key-delay note. So the real driver is floatinghotel.

**Options**
1. **Docs plus a guard helper (about 15 lines).** Add `ctx.pressed_within(action, scope_id)`, which consumes only when `focus_in_subtree(scope_id)`, and document "most specific scope polls first". Ordering is still the app's job, through system order. It is cheap, but it does not solve the ordering problem floatinghotel describes.
2. **Per-entity shortcut handlers (about 100 lines plus tests). Recommended.** `ComponentConfig::with_shortcut(action, fn)` stores handlers in a `HasShortcuts` component. A `DispatchShortcuts` system in the post-update bridge walks from `focus_id` up the parent chain, then to handlers on the UI root. The first handler that returns true consumes `last_action`. Input gates (modals) apply because handlers on gated entities are skipped. App systems that still call `pressed()` see only unconsumed actions. Native menus and e2e can trigger the same callback through the action enum. afterhours never learns what a command means.
3. **A full command registry** (named commands, enable state, menu and shortcut display, chords). It is what an editor eventually wants, but it is far too big for one PR and it overlaps floatinghotel's native-menu bridge.

**Recommendation:** option 2. It fixes the ordering problem at the root, reuses `last_action` consumption, the gates and the parent walk that already exist, and leaves the meaning of each action to the app. Rough size: about 100 lines in `context.h`, `components.h`, `component_config.h` and `systems.h`, one test file, and an example.
