# Sun Java Look & Feel Audit: All Screens (2026-02-15)

Audited 72 UI screenshots from the game UI toolkit showcase against the Sun Java Look and Feel Design Guidelines (1999). The following 15 issues are ranked from most impactful to least.

---

## 1. Pervasive Use of Monospaced/Handwritten Typeface Harms Readability

**Severity:** Critical
**Affected screens:** Nearly all screens including buttons, cards, text, text_input, forms, checkboxes, radio_buttons, toggle_switches, setting_row_showcase, stepper_showcase, navigation_bar_demo, pagination, modals, toasts, drag_drop, horizontal_drag, scroll_view, potion_crafting, shop_interface, race_results, kart_select, fighter_menu, deadspace_settings, flight_options, powerwash_settings, sports_settings, parcel_corps_settings, cozy_cafe, empire_tycoon, neon_strike, meters_gauges, circular_progress, file_tree, animation_basic, animation_declarative, animation_interactive, animation_looping, animation_spring, language_demo, tab_container, tabbing, separators, self_align, bevel_borders, nine_slice_borders, example_borders, decorative_frame, decorators, absolute_positioning, adaptive_scaling, flex_alignment, hstack_showcase, vstack_showcase, layout, layout_bug_repros, auto_text_color, accessibility, colors, themes, text_overflow, text_shadow, text_stroke, images, simple_button, button_variants
**Problem:** The toolkit overwhelmingly uses a monospaced, handwritten-style font (appears to be "Gaegu-Bold" per the language_demo screen) as the default typeface across all UI elements -- labels, body text, buttons, headers, and form controls. The Sun Java L&F guidelines specify that UI text should use proportional sans-serif fonts (SansSerif/Dialog logical fonts at 12pt for standard controls) to maximize legibility. Monospaced handwritten fonts reduce reading speed, look unprofessional in form contexts, and are especially problematic at small sizes where character shapes become ambiguous.
**Guideline:** Typography -- readable font sizes, proper hierarchy; Visual Design -- clean, professional appearance
**Fix:** Replace the default typeface with a proportional sans-serif font (e.g., the system SansSerif logical font) for all standard UI controls, labels, and body text. Reserve the handwritten/monospaced font for decorative titles or thematic headers only. Ensure body text is at least 12pt equivalent and labels use the same font family for consistency.

## 2. Text Clipping and Overflow Across Multiple Screens

**Severity:** Critical
**Affected screens:** cards (text "This panel uses opacity to create a translu..." is clipped), fighter_menu (sub-tab labels "System Opt", "Game Optic", "Display Opt", "Sound & La", "Network Op", "Button Settings" are all truncated), stepper_showcase (card selector shows "HealerWarriorMage" as a single run-together string with no spaces), modals (all right-side buttons clipped: "Simple M...", "Info Dia...", "Op...", "Backgroun...", "Confirm:..."), empire_tycoon ("Trending Up (arrow)" label gets clipped at right edge), horizontal_drag ("Rea..." tag is clipped at right edge), text_overflow (intentional demo but shows red-corner overflow warnings), cozy_cafe ("Patience: Lo..." text overlaps), kirby_options ("Configure vibration, save data, and autosa..." clipped), parcel_corps_settings ("SIGN UP A BUSINESS TO YOUR DELIVERY APP" text runs off screen), nine_slice_borders ("This is a dialog using 9-slice. Corn..." clipped)
**Problem:** Text content is frequently truncated, clipped, or overflows its container across many screens. In several cases (fighter_menu, modals), this makes controls completely unreadable or unlabeled. The Sun Java guidelines mandate that all labels must be fully visible and that containers must size to accommodate their content text.
**Guideline:** Controls -- standard control appearance and behavior; Layout -- proper spacing and alignment; Feedback -- clear status indication
**Fix:** Implement text ellipsis with tooltips for genuinely constrained spaces. For navigation tabs and buttons, size containers to fit their text content. Add minimum width constraints to prevent label truncation. Validate all text-containing components against their actual string lengths.

## 3. Inconsistent and Non-Standard Focus Indicators

**Severity:** Critical
**Affected screens:** buttons (dashed white rectangle around "Normal"), button_variants (dashed outline on top-left "Normal"), animation_basic (dashed border on "Restart Animations"), animation_interactive (dashed border on "Click!"), animation_declarative (dashed border on "Hover"), checkboxes (dashed outline on "Primary"), forms (dashed outline on "Volume: 75%"), radio_buttons (no visible focus ring at all on radio indicators themselves), text_input (thin dashed outline on "Username"), tabbing (yellow thick border on "OPTION A"), setting_row_showcase (white dashed border on "Music" toggle), file_tree (dashed outline on "Home"), shop_interface (dashed outline on "Buy" tab)
**Problem:** Focus indicators are wildly inconsistent across the toolkit. Some use dashed white rectangles, some use colored borders (yellow in tabbing), some use thin outlines barely visible against dark backgrounds, and some controls appear to have no focus indication at all. The Sun Java L&F specifies a consistent, high-contrast focus rectangle (typically a thin dotted line inside the component) that should be uniform across all focusable components.
**Guideline:** Accessibility -- keyboard navigation; Controls -- standard control appearance; Platform Consistency
**Fix:** Standardize on a single focus indicator style across all components. Use a 2px solid contrasting-color border (or the standard Java dotted focus rectangle) that is consistent in color, width, and offset from the component edge. Ensure the focus ring meets WCAG 2.1 minimum contrast requirements (3:1 against adjacent colors).

## 4. Lack of Standard Menu Bars and Keyboard Shortcut Conventions

**Severity:** Major
**Affected screens:** aim_chat (has File/Edit/Insert People menu bar but this is the only screen with a traditional menu bar), fighter_menu (has top-level tabs but no standard menu), deadspace_settings (has pause menu list but no menu bar), all game settings screens (angry_birds_settings, casual_settings, islands_trains_settings, mini_motorways_settings, powerwash_settings, sports_settings, kirby_options, parcel_corps_settings, flight_options), cozy_cafe, empire_tycoon, neon_strike, rubber_bandits_menu, potion_crafting, shop_interface, race_results, kart_select
**Problem:** Out of 72 screens, only the aim_chat screen implements a standard menu bar with File/Edit menus. No screens show keyboard accelerators (Ctrl+S, Ctrl+Z, etc.) or mnemonic underlines in menus. The flight_options screen shows Enter/Esc key bindings at the bottom but this is the exception. The Sun Java L&F guidelines require that all applications provide a standard menu bar with Edit menu (at minimum) containing Cut/Copy/Paste and that all menu items expose keyboard shortcuts.
**Guideline:** Menus -- standard menu patterns, keyboard shortcuts; Accessibility -- keyboard navigation
**Fix:** Add a standard menu bar to application-level screens. Ensure common operations (Save, Copy, Paste, Undo) are accessible via standard keyboard shortcuts. Add mnemonic underlines (Alt+key) to all menu items. For game-specific screens, at minimum provide Esc-to-close and standard key bindings documented in the UI.

## 5. Wildly Inconsistent Dialog Button Ordering and Styling

**Severity:** Major
**Affected screens:** angry_birds_settings (OK green, Cancel white-outlined, Apply blue -- three different styles), casual_settings (OK green, Cancel teal-outlined, Apply teal-outlined), mini_motorways_settings (OK teal, Cancel outlined, Apply outlined), flight_options (OK blue-filled, Cancel outlined, Apply outlined), powerwash_settings (OK blue-filled, Cancel outlined, Apply outlined), text_input (OK teal, Cancel gray, Apply teal), deadspace_settings (OK teal, Cancel white, Apply white), sports_settings (no OK/Cancel/Apply visible in main area)
**Problem:** Dialog action buttons (OK, Cancel, Apply) show no consistent styling convention. The "OK" button is sometimes green, sometimes blue, sometimes teal. Cancel and Apply buttons alternate between outlined and filled styles. Button ordering varies. The Sun Java L&F guidelines specify that OK should always be the leftmost button, followed by Cancel, then Apply, and that the default button (OK) should have a distinct visual treatment (thicker border) while all buttons share the same basic appearance.
**Guideline:** Containers/Windows -- dialog conventions; Controls -- standard control appearance; Platform Consistency
**Fix:** Standardize dialog button bars: order should be OK, Cancel, Apply (or Cancel, Apply, OK per platform convention). The default/primary action button should be visually distinguished only by a thicker border, not a completely different color. All three buttons should share the same basic filled/outlined style. Use a dedicated DialogButtonBar component to enforce consistency.

## 6. Color Used as Sole Indicator of State in Multiple Controls

**Severity:** Major
**Affected screens:** checkboxes (selected state shown only by color change -- Primary row is dark blue with "V", but some checkbox-only squares rely on fill color alone to show state), toggle_switches (ON state is pink/magenta fill, OFF is gray -- no text label or icon differentiator inside the toggle track itself), forms (toggle rows show "X" for enabled which is confusing -- "X" typically means disabled/unchecked), radio_buttons (selected radio shown only by a filled crimson dot vs empty circle), meters_gauges (HP bar uses red/green segments with no pattern or label inside the bar), kart_select (stat bars SPD/ACC/HND/WGT use only color to differentiate), race_results (position points "+15", "+12" etc. shown only in green/yellow -- colorblind users cannot distinguish ranking tiers), circular_progress (each ring variant uses only color to show progress vs. background)
**Problem:** Many controls rely solely on color to communicate state (on/off, selected/unselected, progress level). This directly violates accessibility guidelines. For example, toggle switches show on/off purely through fill color without an icon or text label inside the track. Radio buttons distinguish selected vs. unselected only through fill color of the indicator dot.
**Guideline:** Accessibility -- color not sole indicator; Color Model -- accessible color choices
**Fix:** Add secondary indicators alongside color: checkmarks or "I/O" symbols inside toggle tracks, filled vs. outlined shapes for radio buttons, text percentage labels inside progress bars, and pattern fills or icon overlays for stat bars. Ensure every state can be determined in grayscale.

## 7. Absence of Standard 3D Beveled Borders on Interactive Controls

**Severity:** Major
**Affected screens:** buttons (all button variants use flat filled rectangles with rounded corners), button_variants (filled, outline, ghost -- none have raised/lowered 3D borders), simple_button (completely flat pastel buttons), forms (sliders are flat colored bars), checkboxes (flat colored rows), text_input (purple flat rectangles for input fields), toggle_switches (flat pill shapes), radio_buttons (flat circles), casual_settings/angry_birds_settings (flat mobile-style toggle switches)
**Problem:** The Sun Java Metal Look and Feel relies heavily on 3D beveled borders to indicate interactive affordance. Raised borders signal "clickable/pushable" elements, sunken borders signal "input fields" and "pressed" states. The bevel_borders screen shows the toolkit is capable of rendering raised/sunken bevels, but none of the actual interactive controls (buttons, text fields, checkboxes, toggles) use them. The result is that buttons look like flat colored labels and text inputs look like flat colored rectangles, reducing perceived affordance. While the toolkit demos bevel borders as a decorative feature, it fails to apply them where the Java L&F requires them most.
**Guideline:** Visual Design -- proper use of 3D effects; Controls -- standard control appearance
**Fix:** Apply raised bevel borders (light top-left, dark bottom-right at 1-2px) to all buttons in their default state. Apply sunken bevel borders to text input fields and pressed button states. Use the existing bevel border system shown in bevel_borders for functional components, not just demos.

## 8. No Disabled State Visual Consistency

**Severity:** Major
**Affected screens:** buttons (Disabled button is gray with lighter text), button_variants (Disabled shown as gray for all variant types), flight_options ("Vibration (Unavailable)" shown as grayed text with a "Requires compatible controller" note below), checkboxes ("Disabled", "Disabled ON", "Disabled OFF" shown with reduced opacity), toggle_switches ("Locked Setting (ON)" and "Unavailable Option (OFF)" shown with muted colors and slightly different opacity), forms (no disabled state shown for sliders or toggles), text_input (no disabled text input shown), stepper_showcase (no disabled stepper shown)
**Problem:** Disabled states across the toolkit are inconsistent. Buttons use a fully gray fill. Checkboxes use reduced opacity. Toggle switches use slightly muted colors. Some controls (sliders, text inputs, steppers) do not demonstrate a disabled state at all. The Sun Java L&F guidelines specify that disabled components should use a consistent "etched" appearance: grayed-out text rendered with a light shadow beneath, and the component painted in the control background color with its normal border.
**Guideline:** Controls -- standard control appearance and behavior; Visual Design -- clean, professional appearance
**Fix:** Create a unified disabled rendering strategy: all disabled controls should use the same gray-out treatment (e.g., 50% opacity overlay or consistent gray color token). Disabled text should use the standard disabled text color from the theme. Ensure every interactive component type has a documented and visible disabled state.

## 9. Massive Visual Inconsistency Across Themed Screens (No Platform Consistency)

**Severity:** Major
**Affected screens:** The toolkit renders across at least 6+ completely different visual themes: dark navy (buttons, forms, toggle_switches, setting_row_showcase, etc.), cream/beige Cozy Kraft (cards, cozy_cafe, decorative_frame, layout, simple_button, scroll_view, separators, tab_container), Midnight red/black (colors), pastel green (angry_birds_settings, casual_settings), retro AIM beige (aim_chat), brown/gold (text, potion_crafting, shop_interface), olive/military (islands_trains_settings), bright yellow (rubber_bandits_menu), dark teal (checkboxes, radio_buttons, forms, pagination), neon purple (tabbing), dark sci-fi (deadspace_settings, decorators, neon_strike)
**Problem:** The toolkit showcases radically different visual themes with no shared chrome, window decoration, or structural consistency between them. While theming is a feature, the Sun Java L&F guidelines emphasize that all applications should maintain cross-platform visual consistency. Users should recognize common patterns (window title bars, scroll bars, button shapes) regardless of color scheme. Many theme variations change not just colors but fundamental control shapes, spacing, and typography, making it impossible for users to develop consistent muscle memory.
**Guideline:** Platform Consistency -- cross-platform visual consistency; Visual Design -- clean, professional appearance
**Fix:** Establish a consistent structural framework that persists across themes: standard window chrome, consistent control shapes (button corner radius, toggle proportions, checkbox size), consistent spacing grid, and consistent typography scale. Themes should vary color palette and surface textures only, not fundamental geometry or layout rules.

## 10. Missing or Improper Window Title Bars and Close Buttons

**Severity:** Major
**Affected screens:** angry_birds_settings (uses a circular red "X" in top-right corner of the panel, no title bar), casual_settings (same circular red "X", no standard title bar), islands_trains_settings (circular white "X" in upper right, no title bar), mini_motorways_settings (no close button visible at all on settings panel), flight_options (no window chrome), powerwash_settings ("X SETTINGS" text in top-left but no standard title bar or close button), sports_settings (no title bar), modals (no visible close buttons on modal panels), most demo screens (no window title bars, just content headers)
**Problem:** Almost no screen implements a standard window title bar with the expected title text, minimize/maximize/close buttons. Settings dialogs use inconsistent ad-hoc close mechanisms: circular red X buttons, text links, or no close mechanism at all. The Sun Java L&F requires that all dialogs and secondary windows display a standard title bar with the window title and at minimum a close button in the platform-standard position.
**Guideline:** Containers/Windows -- proper window structure, dialog conventions
**Fix:** Implement a standard DialogFrame component that provides a title bar with the dialog title and a close button. Modal dialogs should additionally include OK/Cancel buttons. Ensure the close button uses the standard platform position (upper-right) and the standard icon, not a custom circular design.

## 11. Inconsistent and Non-Standard Checkbox and Radio Button Indicators

**Severity:** Major
**Affected screens:** checkboxes (uses "V" text character instead of a standard checkmark glyph; "box only" checkboxes are tiny colored squares with no standard border), radio_buttons (uses filled/empty oblongs that look more like elongated pills than standard circular radio indicators), forms (toggle-like controls with "X" marks used where checkboxes would be standard -- "Music X", "SFX X", "V-Sync X")
**Problem:** Checkboxes display a "V" text character rather than a standard checkmark icon. Radio buttons appear as vertically-oriented pill shapes rather than standard circles. The forms screen uses "X" marks to indicate enabled/checked state (opposite of typical convention where X means close/delete). These non-standard indicator shapes reduce recognizability and create confusion about control type and state.
**Guideline:** Controls -- standard control appearance and behavior; Platform Consistency
**Fix:** Use standard checkmark glyphs (Unicode check or rendered path) inside a standard square checkbox frame. Radio buttons should be perfect circles with a filled inner circle for the selected state. Avoid using "X" to indicate positive/enabled state; reserve "X" for close/delete actions. Adopt the standard Java L&F checkbox and radio button rendering.

## 12. Inadequate Spacing and Cramped Layouts

**Severity:** Minor
**Affected screens:** toasts (buttons "Info Toast", "Success Toast", "Warning Toast", "Error Toast" have zero gap between them -- they touch edge to edge), fighter_menu (sub-tab labels are packed with no padding, causing overlap: "System OptGame OpticDisplay Opt..."), hstack_showcase (some items clip at the right edge of the viewport), parcel_corps_settings (left settings panel is very narrow with tight spacing between rows), checkboxes ("box only" row has very tight spacing between the small squares), cozy_cafe ("Patience: Lo..." text overlaps with the progress indicator), sports_settings (setting rows have minimal vertical padding between them), layout_bug_repros (demonstrates multiple spacing issues explicitly)
**Problem:** Many screens exhibit insufficient spacing between interactive elements. Buttons touch each other with no gap, labels overlap their adjacent controls, and form rows have minimal breathing room. The Sun Java L&F guidelines specify minimum 6px padding between related controls, 12px between unrelated groups, and at least 11px vertical spacing between label-control pairs.
**Guideline:** Layout -- proper spacing, alignment, grouping
**Fix:** Enforce a minimum spacing grid: 6px between related controls, 12px between groups, 12px insets from container edges. Add spacing tokens to the theme system and apply them consistently. Ensure no two interactive elements have zero gap between their bounding boxes.

## 13. No Visible Progress or Loading Feedback in Many Interactive Contexts

**Severity:** Minor
**Affected screens:** modals (modal panel sections labeled "BASIC MODALS", "HELPER FUNCTIONS", "MODAL STACKING", "INPUT BLOCKING TEST", "RESULTS" are all empty with no content or loading indicator), drag_drop (no visual feedback for in-progress drag state visible in the static screenshot), cozy_cafe (the "65% Brewed" text in potion_crafting shows progress, but the "0%" progress bar for Oliver's order has no animation or determinate indicator visible), forms ("clipboard empty" status shown but no loading state for paste operation), file_tree ("No selection" status at bottom -- no loading indicator while file tree populates)
**Problem:** Several screens that involve asynchronous operations or staged workflows show no loading indicators, spinners, or progress feedback. Empty panels in the modals screen provide no indication whether content is loading, failed to load, or is simply empty. The Sun Java L&F guidelines require that all operations taking more than 1 second should display a progress indicator, and all empty states should have explanatory text.
**Guideline:** Feedback -- clear status indication, progress feedback
**Fix:** Add indeterminate progress bars or spinners to any panel that loads content asynchronously. Provide empty-state messages ("No items to display" or "Click a button to open a modal") for empty content areas. Ensure all progress indicators include both visual and text representations of progress.

## 14. Non-Standard Tab Control Appearance and Behavior

**Severity:** Minor
**Affected screens:** angry_birds_settings (tabs "Audio", "General", "Info" use a custom style where inactive tabs have a green background overlay), tab_container (Profile/Account/Settings tabs use a completely flat gray style with blue underline indicator), fighter_menu (top tabs Offline/Online/Customize/Options use underline style; sub-tabs below are even more non-standard with crowded text), flight_options (tab bar uses inconsistent font sizes across tabs -- "FLIGHT SYSTEM" is bold, "FLIGHT STICK" is small caps), deadspace_settings (top tabs use all-caps with varying visual weight), mini_motorways_settings (tabs use different font sizes: "Game" is large, "Cross-Save" is tiny), powerwash_settings (tab bar at bottom uses different font sizes to indicate active state), themes (theme list uses a vertical list with bracket indicators "> Ocean Navy <" instead of standard tabs)
**Problem:** Tab controls appear in at least 8 different visual styles across the toolkit. Some use colored backgrounds, some use underlines, some use font-size changes, and some use completely custom bracket notation. The Sun Java L&F specifies that tabs should have a consistent notebook-tab appearance: raised 3D borders on the active tab that visually connects to the content panel, with inactive tabs recessed or pushed back.
**Guideline:** Controls -- standard control appearance; Containers/Windows -- proper window structure; Platform Consistency
**Fix:** Standardize tab appearance using a single TabPane component. Active tabs should be visually connected to their content panel (sharing a border). Inactive tabs should be visually recessed. Tab labels should all use the same font size. Ensure the active tab indicator is not solely a color change.

## 15. Error States and Validation Feedback Largely Absent

**Severity:** Minor
**Affected screens:** text_input (Username, Email, Password fields have no visible validation states -- no red borders, no error messages, no required-field indicators), forms (sliders and toggles have no indication of invalid or out-of-range values), shop_interface (stock shows "3 Low" and "2 Low" in red text for Fire Scroll and Steel Shield, but no structured error/warning component), flight_options ("Vibration (Unavailable)" shows grayed text but no standard disabled tooltip or error explanation), text_overflow (demonstrates text overflow detection with red corners, but this is a debug feature, not user-facing validation), cozy_cafe (no feedback for what happens when trying to serve with 0% completion)
**Problem:** The toolkit provides almost no demonstration of form validation, error states, or constraint feedback. Text input fields show no required-field indicators, no inline validation messages, and no red-border error states. The Sun Java L&F guidelines require that errors be communicated through clear error messages (not just color), that invalid fields be marked, and that the system prioritize prevention (e.g., constraining input) over post-hoc correction.
**Guideline:** Error Handling -- clear error messages, prevention over correction; Feedback -- clear status indication; Accessibility -- color not sole indicator
**Fix:** Add a standard error state to all form controls: red border + error icon + descriptive error message text below the field. Implement required-field indicators (asterisk or "Required" label). Add validation feedback to text inputs (min/max length, format validation). Provide inline success/error feedback for form submission. Use the toast notification system to surface errors for non-field-level issues.
